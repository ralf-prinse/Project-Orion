# Project Overview

Project Orion is a professional deterministic AI-assisted swing trading platform
built as a modern desktop application.

The project is intentionally designed around strict separation of concerns.

The deterministic trading engine performs every calculation.

The desktop layer exists solely to visualize deterministic results.

AI never makes trading decisions.

AI explains deterministic decisions generated by the trading engine.

The long-term objective is to build an institutional-grade desktop trading
platform with a stable architecture that can continue evolving for many years
without requiring architectural rewrites.

---

# Architectural Philosophy

Project Orion is built around five permanent architectural principles.

## 1. Deterministic First

Every calculation must always produce identical results for identical inputs.

No randomness is allowed.

No hidden state.

No GUI influence.

No AI influence.

Deterministic services remain the single source of truth.

---

## 2. Strict Separation of Responsibilities

Business logic never belongs inside the GUI.

Qt widgets never calculate.

Presenters never execute business logic.

Services never generate presentation objects.

Presentation models never contain business rules.

Every layer has exactly one responsibility.

---

## 3. Composition over Inheritance

Project Orion favors composition.

Large classes should be decomposed into smaller collaborating objects.

Workspace presenters compose other presenters.

Workspace coordinators compose workspace presenters.

Widgets compose reusable UI components.

---

## 4. Stable Public APIs

Public interfaces should remain stable.

New functionality should be introduced by extending presentation models rather
than continuously changing workspace APIs.

This minimizes future refactoring.

---

## 5. Evolution without Rewrites

New functionality should fit naturally into the existing architecture.

Architectural changes are only introduced when they clearly reduce future
complexity.

The architecture should evolve—not restart.

# Workspace Composition

GuiWorkspace is now the standard presentation model.

A GuiWorkspace groups every presentation component required by a workspace.

Current supported presentation models:

- GuiMetricCard
- GuiSection

Future presentation models may include:

- GuiChart
- GuiTable
- GuiAlert
- GuiTimeline
- GuiTree
- GuiDockLayout

The Workspace API should remain stable even as new presentation models are
introduced.

---

# Workspace Coordinator

MainWindow remains the application's composition root.

However, MainWindow no longer coordinates individual presentation components.

Workspace composition is delegated to WorkspaceCoordinator.

Responsibilities:

- Coordinate workspace presenters
- Build complete GuiWorkspace objects
- Keep MainWindow small
- Prevent presentation logic from entering the GUI

MainWindow should never assemble cards, sections or future charts itself.

---

# Workspace Presenter Architecture

Workspace presenters coordinate presentation for a complete workspace.

Current implementation:

- PortfolioWorkspacePresenter

Responsibilities:

- Coordinate multiple presenters
- Coordinate presentation services
- Produce one GuiWorkspace

Workspace presenters never perform calculations.

They only compose presentation models.

↓

↓

↓

# Analytics Architecture

Portfolio analytics are intentionally separated from portfolio validation.

Validation:

PortfolioEngine

Analytics:

PortfolioAnalyticsService

Presentation:

PortfolioAnalyticsPresenter

KPI Cards:

PortfolioMetricCardPresenter

Workspace composition:

PortfolioWorkspacePresenter

This prevents individual presenters from accumulating multiple responsibilities.

# Coding Standards

Preferred principles:

- Small classes
- Small files
- Single Responsibility Principle
- Dependency Injection
- Composition over inheritance
- Deterministic services
- Thin GUI
- Stable public APIs
- Presentation through GuiWorkspace
- Reusable presentation models
- No duplicated rendering logic
- No business logic inside Qt widgets

When introducing new functionality, first determine whether it belongs inside:

- a deterministic service
- a presenter
- a workspace presenter
- a workspace coordinator
- a reusable widget

before adding code to existing classes.

# Development Strategy

Future development should prioritize visible user value over architectural
expansion.

Architecture should only evolve when:

- it removes duplication;
- it simplifies future implementation;
- it reduces long-term maintenance;
- a concrete feature requires it.

Avoid introducing abstractions for hypothetical future requirements.

# Guidance for Future AI Sessions

Before proposing new code:

1. Read all project documentation.
2. Respect the existing architecture.
3. Prefer extending existing layers over introducing new ones.
4. Keep MainWindow as the composition root.
5. Keep WorkspaceCoordinator responsible for workspace orchestration.
6. Keep WorkspacePresenters responsible for presentation composition.
7. Keep deterministic services responsible for calculations.
8. Keep Qt widgets responsible only for rendering.

When in doubt:

- prefer composition;
- prefer smaller classes;
- prefer deterministic services;
- prefer reusable presentation models.

# Guiding Principle

Every new feature should fit naturally into Orion's existing architecture.

Before introducing a new class, always ask:

1. Can an existing deterministic service be extended?

2. Can an existing presentation model be reused?

3. Can an existing workspace presenter compose this functionality?

4. Does this belong in a reusable widget instead of a workspace?

5. Will this simplify the architecture rather than complicate it?

If the answer to these questions is yes, Orion's architecture is being
respected.
